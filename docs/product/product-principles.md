# Product Principles

제품 판단의 기준이다. 화면을 만들다가 결정이 갈릴 때 여기로 돌아온다.

## 한 문장 정의

사진과 스크린샷을 넣으면 무엇을 하려던 것인지 알아채고, 그 일을 대신 끝내주는 앱.

## 사용자

대한민국의 일반 사용자. 개발자도 AI 애호가도 아니다.

- 하루에 스크린샷을 여러 장 찍고 그중 대부분을 다시 보지 않는다
- 메신저 대화, 예약 확인, 영수증, 간판, 메뉴판, 안내문을 사진으로 남긴다
- "나중에 처리해야지" 하고 잊는다
- AI에 관심이 있어서 쓰는 것이 아니라, 귀찮은 일이 줄어서 쓴다

이 사용자는 프롬프트를 쓰지 않는다. 사진을 던지고 결과를 기대한다.

## 핵심 UX loop

```
Capture → Understand → Route → Act → Learn
```

| 단계       | 하는 일                            | 사용자가 느껴야 하는 것  |
| ---------- | ---------------------------------- | ------------------------ |
| Capture    | 사진 · 스크린샷 · 공유 시트로 입력 | 넣기가 쉽다              |
| Understand | 내용과 의도를 파악                 | 빠르다                   |
| Route      | 가능한 행동을 제시                 | 내가 하려던 게 저기 있다 |
| Act        | 실제로 실행                        | 끝났다                   |
| Learn      | 반복 패턴을 기억                   | 점점 손이 덜 간다        |

loop의 무게중심은 **Act**다. Understand는 수단이지 제품이 아니다.

## 성공 화면의 정의

성공 화면은 **완료된 행동과 그 결과물**을 보여준다.

**성공 화면이 갖춰야 할 것**

1. 무엇이 끝났는지 한 문장 — "캘린더에 등록했습니다."
2. 결과의 실체 — 등록된 일정 제목, 날짜, 시간
3. 되돌리기 — 실행 취소
4. 다음 행동 한 개 — "캘린더에서 보기"

**성공 화면에 없어야 할 것**

- 신뢰도 점수, 확률, 모델 이름
- 처리 단계 로그
- "AI가 분석을 완료했습니다" 같은 과정 보고
- 축하 애니메이션

분석이 끝난 화면은 성공 화면이 아니다. 일이 끝난 화면이 성공 화면이다.

## AI보다 Action 결과를 우선한다

제품의 가치는 모델의 성능이 아니라 **끝난 일의 수**다.

- 화면의 주인공은 결과물이다. 분석 과정이 아니다
- 정확도를 자랑하지 않는다. 사용자는 정확한 것을 기본으로 기대한다
- 모르겠으면 모른다고 하고 사용자에게 선택지를 준다. 그럴듯하게 지어내지 않는다
- 행동으로 이어지지 않는 분석 결과는 화면에 내보내지 않는다
- 실패했을 때는 실패를 분명히 말하고 수동으로 할 방법을 준다

같은 이유로, 잘 모르는 상태에서 "일단 실행"하지 않는다. 확신이 낮으면 실행 대신 확인을 받는다.

## 한국 사용자 UX 원칙

**언어**

- 기본 locale은 `ko-KR`. 존댓말, 어미 일관 (`~했습니다` / `~해요` 중 하나로 통일)
- 영어 AI 개발 용어(`프롬프트` · `추론` · `confidence` · `routing` 등)를 UI에 노출하지 않는다
- 한국어는 같은 뜻의 영어보다 길다. 버튼 · 탭 · 카드 제목의 줄바꿈과 말줄임을 항상 검증한다
- 어절 중간에서 줄이 끊기지 않도록 확인한다

**형식**

- 날짜 `2026. 8. 16.` / 요일 병기가 유용한 곳에는 `(토)`
- 금액 `12,000원` (기호보다 단위 표기)
- 전화번호 `010-1234-5678`
- 주소는 도로명 기준, 지번 병기가 필요한 경우 보조 표기

**입력 현실**

- 주요 입력은 세로 비율의 모바일 스크린샷이다. 긴 세로 이미지에서 필요한 영역을 찾아야 한다
- 국내 메신저 · 예약 · 배달 · 금융 앱 스크린샷이 큰 비중을 차지한다
- 스크린샷에는 이름, 전화번호, 계좌번호, 주소가 자주 들어 있다. 민감정보 취급을 전제로 설계한다

**기대치**

- 응답이 느리면 쓰지 않는다. 체감 속도가 기능보다 앞선다
- 가입과 권한 요청에 저항이 크다. 가치를 보여주기 전에 요구하지 않는다

## Automation은 사용자 통제 아래 진행한다

Learn 단계는 사용자를 대신해 결정하는 단계가 아니다.

- 자동화는 **사용자가 켜야 켜진다.** 관찰만으로 자동 실행되지 않는다
- 제안은 근거와 함께 한다 — "이런 사진을 최근 5번 모두 지출로 저장하셨습니다. 앞으로 자동으로 할까요?"
- 켜진 자동화는 **한 곳에 모여 보이고**, 언제든 끄거나 고칠 수 있다
- 자동 실행된 뒤에는 그 사실을 알린다. 조용히 하지 않는다
- 되돌릴 수 없는 행동(송금, 외부 발송, 삭제)은 자동화 대상이 아니다. 항상 확인을 받는다

자동화가 늘어날수록 사용자가 통제감을 잃으면 실패한 것이다.

## 신뢰 UX — Undo, Why, Confirmation

사용자가 일을 맡기려면 세 가지가 있어야 한다.

**Undo (되돌리기)**

- 되돌릴 수 있는 실행에는 예외 없이 되돌리기가 붙는다
- 되돌리기는 성공 화면 안에 있다. 설정 깊은 곳이 아니다
- 되돌릴 수 없는 실행은 대신 실행 전에 확인을 받는다. **되돌리기와 사전 확인 중 하나는 반드시 있어야 한다**

**Why (왜 이걸 제안하는지)**

- 제안된 행동에는 근거가 보여야 한다 — "이미지에서 '8월 20일 19시 예약'을 찾았습니다"
- 근거는 모델 내부 설명이 아니라 **사용자가 확인 가능한 사실**이어야 한다
- 사용자가 근거를 고칠 수 있으면 결과도 고칠 수 있어야 한다

**Confirmation (확인)**

- 확인은 위험하거나 되돌릴 수 없을 때만 붙인다
- 안전하고 되돌릴 수 있는 행동에 확인을 남발하면 사용자는 읽지 않고 누른다
- 확인 화면은 **무엇이 실제로 저장/전송되는지** 보여준다

세 가지의 목적은 하나다. 사용자가 "얘한테 맡겨도 되겠다"고 느끼는 것.
