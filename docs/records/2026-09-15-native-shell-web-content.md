# 네이티브 셸 + 웹 콘텐츠로 제품을 나눴다

mobile이 주 제품이고, web은 브라우저 단독 서비스이면서 앱 안 WebView로도 열린다. 같은 화면을 두 번 만들지 않되, 앱다운 부분은 네이티브로 남긴다.

## 상황

제품은 사진 한 장을 넣으면 하려던 일을 끝내 주는 앱이다. 만들 것은 하나인데 클라이언트가 둘(앱 · 브라우저)이라, 어느 영역을 네이티브로 두고 어느 영역을 web 한 벌로 둘지 정해야 했다. 정하지 않으면 두 벌을 계속 만들거나, 반대로 앱이 웹 껍데기가 된다.

## 판단

하이브리드 앱에서 가장 보편적인 분담을 따랐다.

| 영역                                         | 담당                              | 이유                                                                     |
| -------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------ |
| 탭 · 스택 네비게이션, 로그인, 권한, 푸시     | mobile 네이티브                   | 앱다운 사용감, 스토어 심사(App Store 4.2 최소 기능) 안전                 |
| Capture → Understand → Route → Act 핵심 흐름 | mobile 네이티브                   | 카메라 · 사진 · 공유 시트는 네이티브 API이고 제품의 무게중심이 여기 있다 |
| 결과 상세 · 기록 · 공지 · 약관 · 설정 일부   | web 한 벌 → 브라우저 + 앱 WebView | 스토어 배포 없이 고치고, 코드는 한 벌                                    |
| 브라우저 단독 접속                           | web 전체                          | URL 공유, 서버 렌더링된 첫 HTML                                          |

**무게중심이 Act에 있다는 제품 판단이 그대로 경계가 됐다.** 사용자가 하려던 일을 끝내는 흐름은 네이티브에 두고, 끝난 뒤 읽는 화면은 web에 둔다.

## 반영

두 앱은 **코드로 서로를 참조하지 않는다.** 이어지는 것은 URL과 메시지 계약뿐이고, 공유는 `libs/`로만 한다 — DOM 컴포넌트 · RN 컴포넌트 · CSS · 플랫폼 API는 공유하지 않는다.

- Web UI를 React Native에 그대로 복제하지 않는다. 같은 것은 사용자가 얻는 결과이지 화면 구조가 아니다
- 경계는 Nx tag(`type:app` · `type:lib`)와 루트 ESLint 설정이 강제한다
- 새 lib은 두 번째 사용처가 실제로 나타났을 때 만든다. 셋(`webview-bridge` · `auth-contracts` · `onboarding`) 모두 그렇게 생겼다

## 딸려 온 것

WebView 안에서도 데이터 경로는 바뀌지 않는다(web은 여전히 서버에서 API를 부른다, [별도 기록](2026-08-16-web-calls-api-from-server.md)). 대신 앱의 로그인 상태를 WebView가 물려받는 문제가 새로 생겼고, 그것이 [일회용 코드 핸드오프](2026-09-16-webview-login-handoff.md)다.
