# 근거로 보여 준 파일을 에디터에서 바로 연다

DevHub는 판단의 근거가 된 파일을 경로로 보여 준다. 그 코드를 고치려면 경로를 복사해 에디터에서 다시 찾아야 했다. 경로 옆에서 바로 열 수 있게 해 그 한 단계를 없앴다 — 개발 서버로 띄웠을 때만 보인다.

## 상황

DevHub는 근거가 되는 파일을 경로로 보여 주고, GitHub permalink와 경로 복사를 붙여 준다. **읽는 데까지는 충분한데, 고치러 갈 때 한 단계가 남는다** — 경로를 복사하고, 에디터로 옮겨 가서, 그 파일을 다시 찾아야 한다. 하루에도 여러 번 반복되는 동작이다.

## 판단

에디터로 여는 링크(`vscode://file...`)에는 두 가지 부담이 따라온다. 열려면 그 컴퓨터의 **절대 경로**가 필요하고, 주소 형식이 에디터마다 달라 하나를 고르면 다른 에디터를 쓰는 사람에게는 죽은 링크가 된다.

- **절대 경로** — 링크를 만드는 함수가 `NODE_ENV`가 `development`일 때만 값을 낸다. 빌드된 페이지에는 `href`는커녕 요소 자체가 없어, 절대 경로가 그 사람의 브라우저 밖으로 나가지 않는다
- **에디터 고정** — 어느 에디터로 열지는 `DEVHUB_EDITOR`로 고른다. 이름(`antigravity` · `cursor` · `vscode` · `windsurf` · `zed` · `idea` · `webstorm`)이면 아는 주소 형식을, `{path}`가 든 URL을 적으면 그것을 쓴다. 모르는 이름이면 기본값(VS Code)으로 돌아간다 — 설정 오타로 링크가 사라지는 편보다 낫다

여는 대상은 **저장소 안의 파일뿐이다.** 절대 경로(`/etc/passwd`)나 저장소 밖으로 나가는 `../secrets.txt`는 링크가 되지 않는다. 새 규칙을 만든 것이 아니라 GitHub permalink를 만들 때 쓰는 경로 판정을 그대로 통과시킨다([source-link policy](../architecture/devhub.md#22-source-link-policy)).

## 반영

- `apps/devhub/src/lib/editor-link.ts` — 개발 모드에서만 파일의 절대 경로로 에디터 주소를 만든다. 그 외에는 `null`
- `apps/devhub/src/components/editor-link.tsx` — 그 주소를 여는 아이콘 버튼. 아이콘만 있으므로 이름표는 `에디터에서 열기: <경로>`
- 경로가 보이는 두 자리에 같은 모양으로 붙였다 — 상세 정보의 파일 줄(`FileRow`), 문서 · 기록 · 소스 화면 머리(`SourceActions`). **경로 줄 오른쪽은 그 경로에 딸린 행동, 아래 줄은 원격 보기다**

```
문서 · 기록 · 소스 화면 머리
  apps/api/internal/auth/handoff.go                    [에디터] [복사]
  github.com에서 보기 @ 58bc29c · 최신 main에서 보기

상세 정보의 파일 줄
  handoff.go ↗                                         [에디터] [복사]
  internal/auth/
    Handoff.Exchange
```

`[에디터]`는 개발 서버에서만 나온다. 배포된 화면에서는 그 자리에 복사 아이콘만 남고 아래 줄은 그대로다.

## 검증

- `editor-link.spec.ts` 7건 — 배포 모드에서 `null`, 개발 모드에서 절대 경로, 에디터 이름 · 직접 쓴 주소 형식 · 모르는 값의 처리, 저장소 밖 경로 거부
- 렌더까지 확인했다. 배포 모드(`NODE_ENV=production`)에서는 `vscode:` 링크가 아예 없고, 개발 모드에서는 `vscode://file/Users/.../records.ts`가 나온다
- 배치 검사를 두 자리 모두에 더했다(`inspector.spec.ts` · `source-actions.spec.ts`) — 배포 모드에서는 에디터 행동이 0개, 개발 모드에서는 경로마다 복사 버튼 바로 앞에 온다. 아래 줄에는 원격 보기만 남고 구분자가 하나다
- 검사마다 실행 모드를 테스트 안에서 직접 지정한다(`vi.stubEnv`). **로컬 env 파일이 테스트 실행의 `NODE_ENV`를 정한다**(이 머신에서는 개발 모드)는 것을 이 작업에서 확인했고, 모드를 지정하지 않은 검사는 머신에 따라 결과가 갈렸다. 고친 뒤에는 Nx가 그 env 파일을 읽지 않게 하고(`NX_LOAD_DOT_ENV_FILES=false`) 한 번 더 돌려, 결과가 같은 것 — 검사가 로컬 파일에 기대지 않는 것 — 을 확인했다
- 실제로 열리는지는 사용자가 개발 서버에서 눌러 확인했다
